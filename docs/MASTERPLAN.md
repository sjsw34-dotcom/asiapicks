## 1. 무엇을 만드는가

외국인 여행자가 아시아 여행을 결정하고 예약하기 전에 찾는 **믿을 수 있는 기준 사이트**. 첫 전문 영역은 한국.

시간 단위는 수년에서 수십 년이다. 그래서 모든 결정은 "10년 뒤에도 한 사람이 유지할 수 있는가"로 판단한다.
검색 알고리즘, AI 답변 엔진, 제휴사, 프레임워크는 그 사이 여러 번 바뀐다. 바뀌지 않는 것은
**정확한 사실, 출처, 날짜, 그리고 영구 URL**이다. 이 네 가지에 투자한다.

## 2. 영구 원칙

변경하려면 이 문서를 고쳐야 한다. 세션 편의로 우회하지 않는다.

1. **사실은 한 곳에 산다.** 두 페이지 이상에 나오는 요금·날짜·규정은 사실 레지스트리(`src/data/facts/`)에 한 번 적고, 글은 `{{id}}`로 불러온다.
2. **URL은 영구다.** 한 번 공개한 주소는 바꾸지 않는다. 합치거나 내릴 때는 301 또는 410으로 처리한다. 분류(카테고리·동네)는 URL이 아니라 데이터로 표현한다.
3. **유지할 수 있는 만큼만 쓴다.** 발행 속도의 상한은 갱신 능력이다(§5).
4. **사람이 승인한다.** 자동화는 공개·알림·검사만 한다. 글을 쓰거나 승인하지 않는다.
5. **경험을 사칭하지 않는다.** 조사 기반 큐레이션이다. 가상의 필자, 가짜 방문기, 가짜 후기 없음.
6. **사실, 편집 판단, 제휴는 구분해 보여준다.** 제휴사가 추천이 되려면 출처 있는 이점이 있어야 한다.
7. **저장소가 기억이다.** 운영 지식은 대화나 머리가 아니라 이 저장소(문서, 검사, 워크플로)에 남긴다. 몇 달 쉬었다 돌아와도 `CLAUDE.md`와 이 문서만 읽으면 이어갈 수 있어야 한다.

## 3. 정보 구조 (장기형)

```
국가 허브          /korea
  국가 카테고리    /korea/{category}
  국가 단위 글     /korea/{slug}
  도시 허브        /korea/{city}
    도시 카테고리  /korea/{city}/{category}
    동네 페이지    /korea/{city}/{area}
    도시 단위 글   /korea/{city}/{slug}
```

- **글 URL은 3단계에서 멈춘다.** 동네·카테고리는 frontmatter 데이터라 재분류해도 URL이 그대로다.
- **허브는 가이드, 목록 페이지는 탐색.** 허브는 카테고리당 최신 4편만, 전체 목록은 카테고리·동네 페이지가 맡는다.
- **빈 페이지는 만들지 않는다.** 카테고리는 글이 1편 이상, 동네는 소개 글 + 글 1편 이상일 때만 생긴다.
- **다른 나라도 같은 틀.** `/japan/...`를 추가할 때 코드 구조는 바꾸지 않는다(§7 조건 충족 시).

## 4. 사실 레지스트리

글이 늘어도 갱신 부담이 페이지 수가 아니라 **사실 수**를 따라가게 하는 장치. 2026-09-14 도입.

- 위치: `src/data/facts/{country}/{topic}.json`. 항목마다 값, 이전 값, 적용일, 출처, 확인일, 재확인 주기, 효력 종료일.
- 글에서: `{{seoul-subway-fare-card}}` 값, `{{id|number}}` 숫자만, `{{id.previous}}` 이전 값, `{{id.since}}` 적용일.
- 값이 바뀌면 JSON 한 곳만 고친다. 그 사실을 쓰는 모든 페이지가 다음 빌드에 바뀌고, 날짜(`updatedAt`)도 따라가며, IndexNow도 해당 페이지 전부에 간다.
- **효력 종료일(`validUntil`)** 이 있는 사실(K-ETA 면제 기한 등)은 60일 전부터 주간 이슈에 뜬다. 날짜만 바꾸면 되는 연장과, 글을 다시 써야 하는 종료를 구분한다.
- **레지스트리에 넣는 기준:** 2개 이상 페이지에 나오는 사실, 또는 앞으로 여러 글이 인용할 게 확실한 기준값(교통 기본요금, 입국 규정, 주요 입장료). 한 페이지에만 나오는 세부 가격은 그 페이지에 둔다.
- 알 수 없는 id는 빌드를 실패시킨다. 쓰이지 않는 사실은 경고한다.
- **출처 감시(매주 월요일):** 각 사실의 출처 페이지를 받아 우리가 게시한 값이 아직 보이는지 확인한다. 값이 사라지거나 접속이 안 되면 이슈를 연다. **값을 자동으로 바꾸지는 않는다.** 페이지 개편이나 잘못 읽은 값이 모든 글에 한꺼번에 퍼지면 안 되기 때문이다. 사람이 출처를 다시 읽고 레지스트리 한 곳을 고치면, 그다음은 전부 자동이다.
- **감시의 한계:** 뉴스 기사나 공지처럼 한 번 쓰이고 바뀌지 않는 페이지는 새 요금이 다른 URL로 발표돼도 감지하지 못한다. 그래서 사실의 출처는 가능한 한 운영 기관의 상시 요금·규정 페이지로 둔다. 기한이 있는 사실은 `validUntil`이 따로 잡는다.

## 5. 용량 모델: 발행 속도의 상한

매달 필요한 확인 작업은 대략 다음과 같다.

```
월간 확인량 ≈ (레지스트리 사실 수 ÷ 재확인 주기[월]) + (인라인 변동 사실이 있는 페이지 수 ÷ 3)
```

- 첫째 항은 사실 수가 수십~수백 개에서 멈추므로 **평평해진다**.
- 둘째 항은 페이지와 함께 **계속 자란다**. 각 페이지는 자기 출처 중 가장 오래된 것이 90일이 될 때 차례로 올라온다(롤링).
- 그래서 장기적으로 둘째 항을 누르는 것이 핵심이다.
  - 새 글을 쓸 때 반복될 사실은 처음부터 레지스트리로 넣는다.
  - 주제 배합에서 변동 사실이 적은 글(동네 소개, 에세이, 비교 판단)의 비중을 유지한다.
  - 성과 없는 글은 합치거나 내린다(§6).
- **감속 신호:** 월간 이슈의 확인 항목을 그 달 안에 다 처리하지 못한 달이 2개월 연속이면, 발행을 하루 1편에서 줄이고 밀린 갱신부터 처리한다. 틀린 정보가 떠 있는 글 100편보다 맞는 글 50편이 낫다.

## 6. 콘텐츠 수명주기

```
브리프 → 초안(review) → 승인(published, 발행일 예약) → 공개 → 롤링 갱신 → (합치기 | 내리기)
```

- **합치기:** 같은 검색 의도를 두 글이 나눠 갖고 둘 다 약하면, 강한 쪽으로 합치고 약한 쪽은 301.
- **내리기:** 사라진 명소·종료된 서비스·지난 일회성 행사는 410 또는 가장 가까운 글로 301. 계절 글은 내리지 않고 다음 해로 갱신한다(`src/data/calendar.ts`).
- **가지치기 기준(첫 적용 2027-03 이후):** 공개 12개월 이상, 최근 12개월 노출이 거의 없고, 다른 글이 링크로 기대지 않는 글. 판단은 분기 검토에서 사람이 한다.
- 모든 301·410은 `src/data/legacy-urls.json`에 기록한다.

## 9. 위험과 대응

- **AI 답변 엔진이 클릭을 줄인다.** 대응: 인용될 만한 출처가 된다. 사실마다 출처와 확인일, 안정된 URL, 명확한 즉답 문단. 브랜드 검색과 재방문(북마크될 기준 페이지)을 키운다.
- **검색 업데이트로 대량 생산 콘텐츠가 불이익을 받는다.** 대응: 발행 속도보다 정확성. §5 감속 신호를 지킨다. 같은 모양의 글을 찍어내지 않는다(템플릿 규칙).
- **제휴사 정책 변경·종료.** 대응: 제휴 링크는 컴포넌트와 `src/data/offers/`로만 연결되어 한 곳에서 교체 가능. 한 제휴사 의존을 피한다.
- **기술 부식.** 대응: 연 1회 의존성 업그레이드, 검사(`npm run check`)와 테스트가 회귀를 잡는다. 콘텐츠는 MDX + JSON이라 프레임워크를 바꿔도 옮길 수 있다.
- **운영자 공백(몇 달 손을 못 댐).** 대응: 예약 공개는 멈추면 그냥 멈춘다(틀린 글이 나가지 않음). 돌아오면 월간 이슈와 `npm run stale`로 밀린 확인부터 처리한다. 효력 종료 사실은 공백 중에도 이슈로 쌓인다.
- **자산 소실.** 도메인 자동 갱신, GitHub 저장소가 원본, Vercel은 교체 가능한 호스팅이라는 전제를 유지한다.
